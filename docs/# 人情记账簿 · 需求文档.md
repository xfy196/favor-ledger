## 1. 背景与目标

### 1.1 背景

办酒席、随礼、回礼是高频人情场景。靠记忆或纸质礼簿记录存在三个痛点：

- **漏回礼**：收过别人的礼，对方办事时忘了回。
- **回错金额**：记不清对方当时给了多少，回礼给差。
- **查不到历史**：纸质礼簿翻找困难，跨年份、跨事件难以汇总。

### 1.2 目标

产品需要回答两个问题：

- **我收过谁多少？**
- **我欠谁的、哪一笔还没回、回了多少、差多少？**

### 1.3 非目标（v1.0 不做）

- 不做多人实时协作与共享账本（一账号一家庭，经手成员仅为标记）。
- 不做统计图表与报表。
- 不做分次回礼（一收多送），本期一对一配对。
- 不做多币种。

## 2. 用户与使用场景

### 2.1 目标用户

以**家庭**为单位的个人用户。家庭内夫妻、父母的人情往来合并到同一账本，不区分"是谁收的"来算人情，只按"对方是谁"聚合。

### 2.2 核心场景

| 编号 | 场景 | 用户动作 | 期望结果 |
|---|---|---|---|
| S1 | 我办婚礼收礼 | 逐笔录入收礼记录 | 每条收礼成为独立"待回礼"事项 |
| S2 | 朋友结婚我回礼 | 选中该朋友某条待回礼记录，录入回礼金额 | 系统比对金额，显示两清/差多少 |
| S3 | 查看还欠谁 | 打开人情往来 | 看到待回礼的**具体记录**，不只是人名 |
| S4 | 配偶收的礼 | 录入时标记经手成员为配偶 | 仍归入对方名下，家庭合并计算 |
| S5 | 换设备前 | 导出 JSON 备份 | 数据可完整恢复，含配对关系与成员 |

## 3. 核心概念与名词定义

| 名词 | 定义 |
|---|---|
| **家庭账本** | 一个账本对应一个家庭，家庭成员的往来合并计算 |
| **经手成员** | 该笔记录由家庭中谁经手（我/配偶/父亲/母亲/自定义），默认"我"，仅作标记，**不影响人情聚合** |
| **记录 Record** | 一次往来事件：对方 + 方向 + 金额 + 事由 + 日期 + 经手成员 |
| **方向** | `收`（对方给我家）/ `送`（我家给对方） |
| **配对 Pair** | 一条回礼记录关联一条原始收礼记录，形成一对一比对关系 |
| **收礼事项** | 一条收礼记录即一个"待回礼事项"，状态独立 |
| **单次差额** | 配对后：回礼金额 − 该条收礼金额 |
| **两清** | 配对成功且回礼金额 = 收礼金额（严格相等，无容差） |
| **回少** | 配对后回礼金额 < 收礼金额 |
| **回多** | 配对后回礼金额 > 收礼金额（提示，不视为错误） |

## 4. 功能需求

优先级：**P0** 必须有（v1.0） / **P1** 应该有（v1.1） / **P2** 可后续（v2.0）

| 编号 | 功能 | 说明 | 优先级 |
|---|---|---|---|
| F1.1 | 新增记录 | 姓名、方向、金额、事由、日期、经手成员、备注 | P0 |
| F1.2 | 方向切换 | 收礼 / 回礼，默认收礼 | P0 |
| F1.3 | 姓名联想 | 输入时联想历史姓名 | P0 |
| F1.4 | 重名提醒 | 输入姓名与历史完全相同时，提示"已存在同名，确认是否同一人，不同人请加后缀"，**不阻断保存** | P0 |
| F1.5 | 历史提示 | 输入姓名后展示该人历史收/送合计与笔数 | P1 |
| F1.6 | 经手成员选择 | 下拉选择：我 / 配偶 / 父亲 / 母亲 / 自定义，默认"我"，支持成员管理 | P0 |
| F1.7 | 回礼配对 | 创建回礼记录时，展示该人的待回礼收礼记录列表供选择关联；也可选择"不关联" | P0 |
| F1.8 | 编辑记录 | 可改字段；回礼可改配对目标或解除配对 | P0 |
| F1.9 | 删除记录 | 二次确认；删除已配对的收礼记录时提示，并同步解除对应回礼的配对 | P0 |
| F1.10 | 日期默认今天 | 可改 | P0 |
| F1.11 | 记录列表 | 按日期倒序；展示配对状态标签、单次差额 | P0 |
| F1.12 | 搜索 | 按姓名 / 事由 / 备注模糊搜索 | P1 |
| F1.13 | 连续录入 | 保存后保留日期、事由、经手成员，清空姓名与金额，便于酒席批量录 | P1 |
| F1.14 | 快捷金额 | 200/500/800/1000 一键填入 | P2 |

**验收要点**

- 金额为空、≤ 0 或非数字时不可保存，给出明确提示。
- 回礼配对的候选项**只列该人未配对的收礼记录**。
- 删除已配对的收礼记录：回礼记录保留，配对解除，收礼删除后该事项消失。

### 4.2 人情往来模块

| 编号 | 功能 | 说明 | 优先级 |
|---|---|---|---|
| F2.1 | 按人聚合 | 每人：累计收、累计送、笔数、最近日期 | P0 |
| F2.2 | 事项状态统计 | 每人显示：待回礼 N 笔 / 已两清 M 笔 / 回少 K 笔 | P0 |
| F2.3 | 待回礼明细 | 展开某人，列出每条待回礼收礼记录（事由、日期、金额） | P0 |
| F2.4 | 状态标签 | 按人整体状态：有待回礼 / 全部两清 / 回多 | P0 |
| F2.5 | 顶部汇总 | 总收到、总送出、待回礼笔数、待回礼人数、**待回礼收礼金额合计**、**回少差额合计**（两个口径同时展示） | P1 |
| F2.6 | 点击跳转 | 点某人跳到记录页并按该人过滤 | P1 |
| F2.7 | 排序 | 默认待回礼笔数降序，其次待回礼金额降序 | P1 |
| F2.8 | 成员筛选 | 按经手成员筛选查看（如只看配偶经手） | P2 |

**验收要点**

- "待回礼"以**记录**为单位，不因该人其他记录已两清而消失。
- 两清判定严格：回礼金额 = 收礼金额，差 1 分也算回少/回多。
- 家庭合并：我经手与配偶经手的记录，在"对方姓名"维度上合并统计。

### 4.3 数据管理模块

| 编号 | 功能 | 说明 | 优先级 |
|---|---|---|---|
| F3.1 | 云端持久化 | Cloudflare D1，登录后跨设备一致 | P0 |
| F3.2 | 导出 JSON | 全量，含配对关系与成员 | P0 |
| F3.3 | 导出 CSV | 含配对目标、经手成员、状态列 | P1 |
| F3.4 | 导入 JSON | 合并导入，按记录 id 去重；校验配对引用完整性 | P1 |
| F3.5 | 清空数据 | 两次确认后清空 | P0 |
| F3.6 | 成员管理 | 增删经手成员，删除时若被引用则提示 | P1 |

**验收要点**

- 导入时若回礼的 `targetId` 指向不存在的收礼记录，该回礼按"未配对"导入并提示。
- 导出再导入后，配对状态、差额完全一致。

## 5. 数据模型（草案）

### 5.1 记录 Record

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | string | 是 | 唯一标识，导入去重用 |
| person | string | 是 | 对方姓名 |
| direction | enum | 是 | `in` 收 / `out` 送 |
| amount | number | 是 | 人民币，> 0，两位小数 |
| occasion | string | 否 | 事由 |
| date | string | 是 | `YYYY-MM-DD` |
| member | string | 是 | 经手成员，默认"我" |
| note | string | 否 | 备注 |
| targetId | string \| null | 否 | 仅回礼记录：关联的收礼记录 id |
| createdAt | number | 是 | 创建时间戳，用于同日期排序 |

> **配对状态不单独存字段**，由 `targetId` 与对方记录的金额实时推导，避免数据不一致。

### 5.2 家庭配置 Family（D1 `families` / `members`）

| 字段 | 说明 |
|---|---|
| ownerUserId | 归属用户（v1 一人一家） |
| members | 经手成员列表，默认 `["我", "配偶"]` |
| familyName | 家庭名称，v2.0 展示（P2） |

### 5.3 往来关系 Person（实时聚合，不存储）

| 字段 | 说明 |
|---|---|
| name | 对方姓名 |
| recvTotal / giveTotal | 累计收 / 累计送 |
| count | 笔数 |
| pendingCount | 待回礼笔数（未配对收礼） |
| shortCount | 回少笔数 |
| evenCount | 两清笔数 |
| lastDate | 最近往来日期 |

## 6. 业务规则

1. **配对规则**
   - 仅回礼记录可设置 `targetId`，且只能指向**同一 person 的收礼记录**。
   - 一条收礼记录最多被一条回礼记录配对（一对一）。
   - 一条回礼记录最多配对一条收礼记录。
   - 配对可通过编辑解除，解除后收礼记录回到待回礼状态。
2. **状态判定**
   - 收礼未配对 → **待回礼**。
   - 已配对：`diff = 回礼金额 − 收礼金额`；`= 0` 两清，`< 0` 回少（差 `|diff|`），`> 0` 回多（多 `diff`）。
3. **两清定义**：严格相等，**无容差**。
4. **家庭聚合**：按 `person` 聚合时忽略 `member`，我/配偶/父母经手的记录合并；`member` 仅用于筛选展示。
5. **重名规则**：以姓名字符串为唯一标识。输入已存在姓名时提示，但不拦截；不同人由用户加后缀区分。
6. **金额规则**：仅人民币，> 0，两位小数。
7. **排序规则**：
   - 记录列表按日期倒序，同日期按 `createdAt` 倒序。
   - 人情往来按待回礼笔数降序，其次待回礼金额降序。
8. **删除规则**：删除已配对的收礼记录时，先提示，确认后删除并清空对应回礼的 `targetId`。
9. **导入规则**：按 id 去重；配对引用校验，悬空则置空并提示。
10. **待回礼汇总口径**：顶部同时展示两个数——
    - 待回礼**收礼金额合计**（未配对收礼记录金额之和）
    - **回少差额合计**（已配对且回少记录的差额之和）

## 7. 页面与交互结构

```
人情记账簿
├── 记账（默认页）
│   ├── 录入表单
│   │   ├── 姓名（联想 + 重名提醒）
│   │   ├── 方向（收 / 送）
│   │   ├── 金额 / 日期 / 事由
│   │   ├── 经手成员（下拉）
│   │   ├── 【仅回礼】选择待回礼事项（弹出该人未配对收礼列表）
│   │   └── 备注
│   ├── 搜索
│   └── 记录列表（状态标签 / 单次差额 / 编辑 / 删除）
├── 人情往来
│   ├── 顶部汇总（总收 / 总送 / 待回礼笔数 / 待回礼人数 / 待回礼金额 / 回少差额）
│   └── 按人列表 → 展开待回礼明细
└── 数据
    ├── 导出 JSON / CSV
    ├── 导入 JSON
    ├── 成员管理
    └── 清空数据
```

**关键交互**

- 方向切到"回礼"后，姓名输入完成时**动态展示该人待回礼事项**供选择配对；也可跳过（不关联）。
- 记录列表中，回礼记录显示配对信息，如"↳ 配对：张三婚礼 800，两清 / 差 X"。
- 收礼记录显示"待回礼"或"已配对（回 800，两清）"。
- 重名提醒以黄色提示条展示，不打断录入。
- 收/送用不同颜色区分（建议收=红、送=蓝，符合中文语境）。

## 10. 决策记录（原遗留问题定案）

| 编号 | 问题 | 决策 |
|---|---|---|
| D1 | 是否支持分次回礼（一收多送） | **v1.0 不支持**，一对一配对；分次回礼列入 v2.0 待办 |
| D2 | 已配对收礼能否撤销后重新配对 | **允许**，通过编辑回礼记录解除或改配对目标 |
| D3 | 删除经手成员时其名下记录如何处理 | **保留原字符串**作为成员名，并在删除时提示影响条数，不强制迁移 |
| D4 | 家庭名称是否 v1.0 展示 | **不展示**，数据层预留，v2.0 再上线 |
| D5 | 顶部"待回礼"汇总口径 | **两个口径同时显示**：待回礼收礼金额合计 + 回少差额合计 |

## 11. 验收标准（v1.0 MVP）

- [ ] 录入收礼 800（张三婚礼），该记录显示"待回礼"。
- [ ] 录入回礼时能选到该待回礼事项；回 800 后双方显示"两清"，单次差额 0。
- [ ] 回 500 后显示"回少 300"。
- [ ] 回 1000 后显示"回多 200"。
- [ ] 同一人另一条收礼仍保持"待回礼"，不因上一笔两清而消失。
- [ ] 输入已存在姓名时出现重名提醒，但可继续保存。
- [ ] 配偶经手与本人经手的记录，在人情往来中合并到同一对方名下。
- [ ] 删除已配对收礼后，回礼配对解除并提示。
- [ ] 编辑回礼可解除配对，原收礼恢复"待回礼"。
- [ ] 导出 JSON → 清空 → 导入，配对关系与状态完全恢复。
- [ ] 移动端可完成录入、配对、查看。
